# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Sprachgesteuerter Entwicklungs-Assistent (multi-phase build, all 4 planned phases now implemented): user speaks into the mic, Gemini Live API responds with voice, a Flet desktop window shows connection status and a running transcript, plays two alternating personas (Duo-Mode), and a silent background critic can inject logic-error hints into the conversation. All in-code comments, docstrings, UI strings, and README are in German — match that when editing.

The full 4-phase roadmap and the 4 key design decisions behind it (why one AI plays both personas instead of switching connections, why speech rate control was dropped, etc.) live in `README.md` — read it before proposing architecture changes.

## Commands

Setup (Windows):
```
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

Run:
```
python main.py
```

Tests:
```
pytest
```
Run a single test: `pytest tests/test_duo_mode.py::test_next_role_toggles`. There is no lint or build tooling configured. The `tests/` suite (`test_config.py`, `test_sessions.py`, `test_duo_mode.py`, `test_background_critic.py`, `test_code_context.py`, `test_session_memory.py`, `test_dev_tools.py`, `test_discord_audio.py`, `test_reconnect.py`, `test_gemini_session.py`) covers the pure-logic modules plus `GeminiLiveSession`'s connection lifecycle — no mic/speaker/Gemini network involved; `test_gemini_session.py` monkeypatches `gemini_session.genai.Client` with a `FakeClient` whose `FakeSession.receive()` yields exactly one turn per call, like the real SDK; `BackgroundCritic.check()` is tested against a fake `client.aio.models.generate_content` (see the `_FakeClient` classes in `test_background_critic.py`), not the real API — same pattern in `test_session_memory.py`. `test_dev_tools.py` injects a fake `runner` coroutine into `dev_tools.run_tool()` instead of running real subprocesses. `main.py` (the Flet UI) and `discord_bridge.py` have no automated tests, and `gemini_session.py` is only tested against fakes — verify changes by actually running `python main.py` (see the flet-version gotcha below before assuming a fresh window opens cleanly), or at minimum `python -c "import ast; ast.parse(open('main.py', encoding='utf-8').read())"` plus importing the non-GUI modules directly to catch syntax/import errors — `main.py` itself can't be imported without triggering `ft.run(main)` at module scope. When testing `main.py` manually, temporarily edit `config.json`'s `duo_mode`/`critic_enabled` to exercise those code paths, then restore it — `config.json` holds a real API key, don't leave it in a broken/half-edited state. Function-Calling (`dev_tools.py`'s allowlist wired into `gemini_session.py`) has specifically **not** been exercised against a live connection — its `tools=`/`FunctionResponse` shapes were only checked to construct without error against the installed SDK, never a real round-trip; treat it as unverified until manually tested.

Config: copy `config.example.json` to `config.json` and set `api_key` (Gemini API key from Google AI Studio). `config.json` holds a real secret — never print its contents or commit it.

**flet version gotcha:** `requirements.txt` pins `flet>=0.24.0` (unbounded), but what actually gets installed is the current release, which as of this writing is `0.86.x` — a significantly newer API generation than 0.24, not just a patch bump. Notably: `page.window_width`/`page.window_height` don't exist anymore (use `page.window.width`/`page.window.height`); dialogs use a stack-based `page.show_dialog(dialog)` / `page.pop_dialog()` API instead of setting `dialog.open = True/False` + `page.update()`. Always check `dir(ft.Page)` / `inspect.signature(...)` against what's actually in `.venv` before assuming a Flet API from memory or older docs still applies — the two generations differ enough that plausible-looking old-style code fails silently or with `AttributeError` at runtime, not at parse time.

## Architecture

Thirteen modules (two of them only for the separate Discord entry point), wired together in `main.py`:

- **`config.py`** — `AppConfig` dataclass loaded from `config.json` (or `GEMINI_API_KEY` env var as fallback for the key). Raises `SystemExit` with a German error message if no valid key is found. Fields include `input_device`/`output_device`, `duo_mode` (`"off"`/`"auto"`/`"manual"`), `critic_enabled`, `critic_model`, `critic_check_every`. `AppConfig.save_settings(config_path="config.json", **fields)` is a static helper that merges arbitrary keys into `config.json` without touching the rest — `save_voice(voice, ...)` is a thin wrapper around it, kept for readability at call sites. Voice and duo_mode only take effect on the next connect (both are baked into `LiveConnectConfig`/`system_instruction` at connect time), so saving writes to disk but doesn't hot-swap the live session.
- **`sessions.py`** — Conversation history persistence. `save_session(transcript: list[dict])` writes the in-memory transcript log (`[{"who": ..., "text": ...}, ...]`) to a timestamped JSON file under `sessions/`. `list_sessions()` / `load_session(path)` read them back. Loading a session is read-only display — it does not resume any live Gemini conversation context, it's just replaying old text.
- **`duo_mode.py`** (Phase 3) — Pure logic, no I/O. `build_system_instruction(base, mode, start_role=...)` appends Duo-Mode rules to the base `system_instruction` depending on mode: `"auto"` tells the model to switch roles after every response on its own; `"manual"` tells it to hold a role until told otherwise. `next_role(current)` toggles between `ROLE_VISIONAER`/`ROLE_PRAGMATIKER`. `build_switch_message(role)` builds the invisible text nudge sent via `send_text()` for manual switches. There's no way to detect which role the model is *actually* in for `"auto"` mode — only `main.py`'s locally-tracked `current_role` state (used for manual mode's UI label) is authoritative, and only for manual mode.
- **`background_critic.py`** (Phase 4) — The closed-loop critic. `build_critic_prompt(transcript_log, window=12, code_snippet=None, prior_hint=None)` and `parse_critic_response(text)` are pure functions (prompt in, `"OK"` or `"HINWEIS: ..."` parsed out). The optional `code_snippet` (typically the live clipboard content, threaded in from `main.py`) gets its own labeled section in the prompt ("Code-Ausschnitt aus der Zwischenablage:") ahead of the transcript, and `CRITIC_PROMPT_HEADER` explicitly tells the model to cross-check claims like "das ist jetzt gefixt" against it; the optional `prior_hint` gets its own section too ("Offener Punkt aus letzter Sitzung:") with an instruction to check whether it's now resolved — both sections are omitted entirely (no instruction change needed) when their argument is `None`/blank, so behavior for the plain-brainstorm case is unchanged. `extract_last_hint(records)` is the cross-session half: scans saved session records (from `sessions.load_session()`) backwards for the last entry with `who == "Kritiker"` and returns its text, or `None`. That convention — `main.py`'s `run_critic_check()` appending `{"who": "Kritiker", "text": hint}` directly to `transcript_log` (not via `add_transcript_line()`, to avoid re-triggering `register_turn()`/the styled speech-bubble UI) — is what makes hints round-trip through `save_session()`/`load_session()` for free, no schema change needed. `wrap_hint(hint)` builds the invisible text nudge sent via `send_text()`. `BackgroundCritic` ties it together: `register_turn(who)` counts user turns and returns `True` every `check_every` turns (call site decides what to do with that); `check(transcript_log, code_snippet=None, prior_hint=None)` makes a **separate, non-live** `client.aio.models.generate_content()` call (not the Live API — a plain text completion) and returns the parsed hint or `None`. Network/API errors inside `check()` are caught and swallowed (returns `None`) — a broken critic must never crash the live voice session, only silently skip that round.
- **`audio_engine.py`** — `AudioEngine` owns the `sounddevice` input/output streams, running in their own audio threads. Mic input is captured at 16 kHz (`INPUT_RATE`, what Gemini expects), playback is at 24 kHz (`OUTPUT_RATE`, what Gemini returns) — these rates are asymmetric by design, don't unify them. Mic callback pushes int16 PCM chunks into `mic_to_gemini` (an `asyncio.Queue`, bridged from the audio thread via `loop.call_soon_threadsafe`); when full, oldest chunk is dropped to stay live. Playback works the opposite direction: `speaker_feeder()` (an asyncio task) drains `gemini_to_speaker` into a `deque` of chunks that the output stream's callback pulls from under a `threading.Lock`, since that callback runs on the audio thread, not the event loop. `clear_playback()` is called on user-interrupt to stop the AI from "talking over itself". `list_audio_devices()` is a module-level function (not a method) used for the startup diagnostic printout.
- **`code_context.py`** (Code-Kontext-Grounding) — Pure logic, no I/O in the formatting function. `build_context_message(clipboard_text, max_chars=4000)` turns raw clipboard text into the invisible German system-hint text sent via `send_text()`; returns `None` for empty/whitespace-only input, truncates and appends a "(gekürzt)" note past `max_chars`. `read_clipboard(paste_fn=None)` is the one I/O wrapper — defaults to `pyperclip.paste`, but accepts an injectable `paste_fn` so it stays unit-testable without a real clipboard; like `BackgroundCritic.check()`, any exception (no clipboard access, `pyperclip` missing a backend, etc.) is swallowed and returns `None` rather than crashing the live session. There is no git-diff variant — the project itself isn't a git repo, so that path was dropped rather than built untested.
- **`session_memory.py`** (Cross-Session-Gedächtnis) — Pure prompt-building (`build_summary_prompt`, `build_resume_message`) plus one I/O function, `summarize_session(client, model, records)`, that makes a **separate, non-live** `generate_content()` call — exact same pattern as `BackgroundCritic.check()`, including swallowing every exception and returning `None`. `records` come straight from `sessions.load_session()`; an empty list returns `None` without ever calling the model. `main.py` wires this at connect time only (not per-turn): `handle_status()` watches for the exact string `"Verbunden"` (not `"Verbunden (unterbrochen)"`, which also starts with "Verbunden" but isn't a fresh connect) and fires `send_resume_context()` exactly once per `session.run()`, via a `resume_sent` flag — it loads the most recent session from `list_sessions()[0]` (skipped if none exist), summarizes it, and — only if a non-empty summary came back — injects it via `session.send_text()`. Reuses `config.critic_model` as the summarizer's text model (and `text_client`, a single shared `genai.Client`) rather than adding a new config field — that field already means "cheap non-live text model for background calls" and exists in `AppConfig` regardless of `critic_enabled`.
- **`dev_tools.py`** (Function-Calling) — Lets the model actually *run* something (`pytest`, `git status/diff/log`) instead of only talking about it, closing the loop that `code_context`/`background_critic` opened: from "sees code" to "verifies code". `ALLOWED: dict[str, list[str]]` maps a fixed set of names to a fixed, hardcoded `argv` — the model can only ever pick a `name` (enforced by an `enum` in `build_tool_declaration()`'s JSON Schema), it can never supply its own arguments or free text, so there is no injection surface. `run_tool(name, runner=None, cwd=None, timeout=30.0)` rejects unknown names *without invoking `runner` at all*; `runner` defaults to `_default_runner`, which uses `asyncio.create_subprocess_exec` (never `subprocess.run`/`shell=True`, so a hung process — an infinite test loop — can't block the event loop / stall the mic and speaker queues) and kills the process on timeout rather than leaving it running in the background. Deliberately does **not** follow the `BackgroundCritic`-style "swallow errors, return `None`" pattern: a non-zero exit code (failing tests) is a valid, speakable answer, not a failure — `run_tool` always returns a string, reserving actual error text for genuine execution problems (unknown command, timeout, missing binary). `format_result()` truncates long output the same way `code_context.build_context_message()` does. `cwd=None` means the subprocess inherits the running `python main.py` process's working directory — i.e. wherever the user launched it from, per the Commands section above; this is correct for a real user run, but means these tools were never exercised against a live connection from *this* worktree job (see `gemini_session.py` note below).
- **`reconnect.py`** — Pure logic. `is_fatal(exc)` decides whether retrying is pointless (close codes 1007/1008, 4xx except 408/429, `ValueError`/`TypeError`/`AttributeError`) vs. transient (1006/1011/5xx/`OSError`/timeouts). `ReconnectPolicy`: exponential backoff with jitter, `max_attempts`, and `connection_ended(lasted)` resets the counter after a connection held `stable_after` seconds. Used by both `GeminiLiveSession` and the Discord voice watchdog.
- **`gemini_session.py`** — **`session.receive()` in google-genai ends after every completed turn** (`turn_complete`) — `_receive_loop` therefore wraps it in `while True:`; a closed socket makes `receive()` raise, so this doesn't spin. Without that loop the whole session ended after the first answer (regression test: `test_receive_continues_after_first_turn`). `run()` is a reconnect loop around `_run_once()` (one connection): non-fatal errors and normal closes reconnect via `ReconnectPolicy`, fatal ones raise; `auto_reconnect=False` restores the old single-connection behavior. With `config.session_resumption` (default on) it sends `SessionResumptionConfig(handle=...)` + sliding-window `ContextWindowCompressionConfig`, stores `session_resumption_update.new_handle`, and if connecting *with* a handle fails before reaching "Verbunden" it drops the handle and retries fresh. `go_away` sets `_reconnect_now` once the model isn't mid-turn (tracked via `model_turn` / `turn_complete`/`interrupted`), else via a `call_later` timer at `time_left - GO_AWAY_MARGIN` (timer cancelled when the connection ends); go_away + handle reconnects immediately without counting an attempt. Each `_run_once()` calls `audio.clear_mic_queue()` (if present) right after connecting. Status strings during reconnect: `"Verbindung verloren – neuer Versuch in N s …"` / `"Verbinde neu …"` — neither starts with `"Verbunden"`, so `main.py`'s `resume_sent` logic is unaffected. `GeminiLiveSession` opens one `google-genai` Live API connection per attempt (`client.aio.live.connect`) and runs `_send_loop` (mic queue → `session.send_realtime_input`) and `_receive_loop` (`session.receive()` → routes audio to `audio.gemini_to_speaker`, transcript text to `on_transcript`, and tool calls to `_handle_tool_call`) as concurrent tasks alongside a stop-event waiter, via `asyncio.wait(..., FIRST_COMPLETED)`. `_is_normal_close()` distinguishes a clean server-side close (code 1000 / `ConnectionClosedOK`) from a real error — only real errors propagate up. `content.interrupted` from the server triggers `audio.clear_playback()`. `send_text(text, interrupt=False) -> bool` never raises (returns `False` when not connected or on send failure — callers fire it as a background task) and injects invisible text turns into the live session — used by `duo_mode`'s manual role switch, `background_critic`'s hints, `code_context`'s clipboard hint, and `session_memory`'s resume summary. It sends `turn_complete=interrupt`, default `False`: on `gemini-3.8-live` (the default `model`), `turn_complete=True` *unconditionally interrupts* active generation, while without it the server holds the content until the next message — matching every hint text's "bring it up casually" wording. Don't flip the default back to `True` without that in mind. `LiveConnectConfig(tools=[types.Tool(function_declarations=[dev_tools.build_tool_declaration()])])` registers the Function-Calling allowlist; tool-call messages arrive on `message.tool_call` (**not** `message.server_content` — verified directly against the installed `google-genai` SDK via `inspect`/`model_fields`, since `_handle_message()`'s `if content is None: return` guard would otherwise silently eat them), handled by `_start_tool_calls()` — one background task per function call (tracked in `self._tool_tasks` by `call.id`, so `message.tool_call_cancellation.ids` can cancel individual ones; all cancelled when a connection ends), **not** awaited inside `_receive_loop`, because `gemini-3.8-live` calls tools `NON_BLOCKING` by default and keeps talking; awaiting a up-to-30 s `pytest` there would stall all incoming audio: runs each requested command through `dev_tools.run_tool()`, wraps the result in `types.FunctionResponse(id=call.id, name=call.name, response={"output": ...})`, with `scheduling=WHEN_IDLE` (result is worked in once the model finishes its current utterance rather than cutting it off), and replies via `session.send_tool_response(function_responses=...)`. **Unverified against a live connection** — this job can't run `python main.py` (no mic/speaker/real API in this environment); the `tools=`/`FunctionResponse`/`send_tool_response` shapes were confirmed to construct correctly against the installed SDK's pydantic models (no validation errors, no network call), but the actual round-trip (model requests a tool, gets a sensible reply, keeps talking) has not been exercised end-to-end — verify by hand before relying on it. Note: the Live API's `SpeechConfig` only supports `voiceConfig` + `languageCode`, no speech-rate/speed parameter — don't add a "Sprechtempo" setting that assumes the API accepts one (confirmed by inspecting `google.genai.types.SpeechConfig`'s signature).
- **`discord_audio.py`** (Discord-Voice-Bridge) — Pure audio logic, no Discord import. `DiscordAudioAdapter` duck-types `AudioEngine` (`mic_to_gemini`, `gemini_to_speaker`, `clear_playback()`) so `GeminiLiveSession` is reused unchanged. `discord_to_gemini()` (48k stereo → 16k mono, boxcar decimation), `GeminiToDiscordResampler` (24k mono → 48k stereo, stateful across chunks), `FrameRingBuffer` (Discord's player thread *pulls* exactly `FRAME_BYTES` = 3840 every 20 ms — no own timer, so no clock drift; silence on underflow; `barge_in()` clears and opens a time-bounded discard window, `release()` closes it — called from `clear_playback()` on Gemini's `interrupted`), `SpeakerGate` (first speaker holds the floor until `hold_seconds` of silence; others dropped). Speaker-change notes are `str` items in the same `mic_to_gemini` queue as the audio `bytes` (guarantees ordering); `GeminiLiveSession._send_loop` sends `str` items via `send_realtime_input(text=)`, not `send_client_content` (which would end the user's turn). `gemini_session.py` imports `AudioEngine` only under `TYPE_CHECKING` so the bridge doesn't need sounddevice/PortAudio.
- **`discord_bridge.py`** — Separate entry point (`python discord_bridge.py`), needs `discord_token` + `discord_voice_channel_id` in config. Uses `discord.py` for sending and `discord-ext-voice-recv` for receiving (discord.py itself can't receive voice; voice_recv also provides the per-SSRC jitter buffer). Passes `enable_tools=False` to `GeminiLiveSession` — any channel member could otherwise trigger `pytest`/`git` on the host. **Never run against real Discord** — and `discord-ext-voice-recv` 0.5.2a has no DAVE (Discord voice E2EE) handling, so receiving may not work at all on DAVE-enforced channels; verify by hand. Robustness: `_voice_watchdog()` checks every `WATCHDOG_INTERVAL` s — rejoins (with `ReconnectPolicy`, never giving up) only after two consecutive not-connected checks so it doesn't fight discord.py's own voice reconnect, restarts `listen()`/`play()` if their threads died (`after` callbacks only log — they run off-loop), and logs frame stats every minute. `GeminiSink.write`/`GeminiSource.read` swallow all exceptions (one would kill voice_recv's reader / discord.py's player thread). If any of the feeder/Gemini/watchdog tasks ends, the whole bridge shuts down with exit code 1.
- **`main.py`** — Flet app entry point (`ft.run(main)`). Design tokens (`BG_COLOR`, `USER_BUBBLE_COLOR`, `KI_BUBBLE_COLOR`, `ACCENT_*`, `ROLE_BUBBLE_COLORS`, `STATUS_COLORS`) are module-level hex-string constants at the top, deliberately reusing the same accent colors as the README architecture diagram (critic=green, session-memory=amber, tools=red, code-context=blue) so color consistently signals *which feature* is speaking, not just decoration — `add_system_note(text, color=...)` takes that color per call site. Builds the UI (status dot — pulsing via `pulse_status_dot()`, a background task using only `Container.animate_opacity`/`.opacity`, no new dependency, dimming in and out only while status is "connected", to read as "listening" — transcript `ListView`, a `FilledButton` mute button as the one primary/text action, settings gear icon with voice + duo_mode dropdowns and a `critic_enabled` switch, and four secondary actions — save/open sessions, "Rolle wechseln" (visible only when `duo_mode == "manual"`), "Code-Kontext senden" — deliberately `IconButton`s with tooltips rather than text buttons, to avoid five equally-weighted text buttons crowding one row). `add_transcript_line` colors KI bubbles by `current_role` (`ROLE_BUBBLE_COLORS`) only when `config.duo_mode == "manual"` — the one mode where `current_role` is actually authoritative (see the `duo_mode.py` entry above) — and falls back to the generic `KI_BUBBLE_COLOR` for `"off"`/`"auto"` rather than guessing a role it can't actually know. Constructs `AudioEngine` and `GeminiLiveSession` wired via callbacks (`on_status`, `on_transcript`), starts `audio.start()` then runs `session.run()` as the main coroutine, with `speaker_feeder()` and `pulse_status_dot()` as background tasks (both cancelled in the `finally` alongside `feeder_task`). `do_send_context()` reads the clipboard via `code_context.read_clipboard()`, builds the hint via `code_context.build_context_message()`, and — only if `session.session is not None` (i.e. actually connected) — fires `session.send_text()` as a background task; a no-op with a status message otherwise, same pattern as `do_switch_role()`. Rewrites `config.system_instruction` via `duo_mode.build_system_instruction()` right after loading config, before constructing `GeminiLiveSession` — that's the single integration point, `gemini_session.py` itself is untouched by Duo-Mode. Maintains an in-memory `transcript_log` list (appended to in `add_transcript_line`, which also backs the "Sitzung speichern" button); if a `BackgroundCritic` is configured, `add_transcript_line` calls `critic.register_turn()` on every line and fires `run_critic_check()` as a background `asyncio.create_task` when it returns `True`; `run_critic_check()` re-reads the clipboard via `code_context.read_clipboard()` on every check and passes it into `critic.check(transcript_log, code_snippet=...)`, so the critic's checks stay current with whatever's on the clipboard at check time, not just what was there when Code-Kontext-Grounding was last manually triggered. `page.on_disconnect` triggers graceful shutdown (`shutdown()`: auto-saves `transcript_log` via `save_session()` if non-empty, then `session.stop()` + `audio.stop()`) — this auto-save is what makes Cross-Session-Gedächtnis reliably have something to resume from, since users don't always remember to click "Sitzung speichern". `on_status` is `handle_status()`, not a plain lambda, precisely so it can also detect the first `"Verbunden"` and kick off `send_resume_context()` (Cross-Session-Gedächtnis) exactly once per connection. `handle_tool_call(command, result_text)` is `GeminiLiveSession`'s `on_tool_call` callback — logs an `add_system_note()` line (truncated to 200 chars) so the user sees which allowlisted dev command the KI ran and what came back, same visibility principle as the critic/resume notes. `add_system_note(text)` appends a small, grey, locally-only line to `transcript_view` — never to `transcript_log`, so it's invisible to the KI/critic/session-memory, purely a UI signal — called right after both silent `send_text()` injections (the critic's hint in `run_critic_check()`, the resume summary in `send_resume_context()`) so the user has visible proof those background features actually fired, instead of the injections being entirely invisible. A `prior_critic_hint: str | None` closure variable, set once by `send_resume_context()` via `background_critic.extract_last_hint()` on the previous session's records, is read (not reassigned, so no `nonlocal` needed there) by every later `run_critic_check()` this connection and passed as `critic.check(..., prior_hint=...)` — best-effort only: if a critic check somehow fires before `send_resume_context()` finishes (both are independent background tasks), it just runs without the prior hint, same as if there were no previous session.

Data flow: mic thread → `mic_to_gemini` queue → Gemini Live API → `gemini_to_speaker` queue → speaker thread, with transcript text and status pushed to the Flet UI via plain callbacks (no framework state management). The background critic is a side-channel: it reads `transcript_log`, makes its own separate API call, and writes back into the live session only via `send_text()` — it never touches the audio path directly.

## Roadmap context (from README)

All 4 planned phases are implemented. Duo-Mode (Phase 3) and the background critic (Phase 4) are both off by default in `config.example.json` (`duo_mode: "off"`, `critic_enabled: false`) — flip them on in `config.json` to use them.
